Here's a PowerShell checklist, in the order I'd actually run them:

**1. Check file permissions (ACLs) on the db file and its folder**
```powershell
Get-Acl "C:\path\to\yourdb.db" | Format-List
Get-Acl "C:\path\to\folder" | Format-List
```
Look at whether the service account running the app has **Write/Modify** rights. Compare against a known-working server if you have one.

**2. Check the read-only file attribute**
```powershell
Get-ItemProperty "C:\path\to\yourdb.db" | Select-Object Name, Attributes
```
If `Attributes` includes `ReadOnly`, that's your answer. Clear it with:
```powershell
Set-ItemProperty "C:\path\to\yourdb.db" -Name IsReadOnly -Value $false
```

**3. Check for leftover journal/WAL/SHM files with different permissions**
```powershell
Get-ChildItem "C:\path\to\folder" -Filter "yourdb.db*" | Select-Object Name, Attributes, Length, LastWriteTime
```
Look for `yourdb.db-journal`, `yourdb.db-wal`, `yourdb.db-shm` sitting next to it. Check their attributes too — a stray readonly journal file blocks writes to the whole db.

**4. Check disk space on that volume**
```powershell
Get-PSDrive -PSProvider FileSystem | Select-Object Name, @{N='FreeGB';E={[math]::Round($_.Free/1GB,2)}}, @{N='UsedGB';E={[math]::Round($_.Used/1GB,2)}}
```
Or for a specific drive:
```powershell
Get-CimInstance Win32_LogicalDisk -Filter "DeviceID='D:'" | Select-Object DeviceID, @{N='FreeGB';E={[math]::Round($_.FreeSpace/1GB,2)}}
```

**5. Check if another process has the file locked**
```powershell
# Requires handle.exe from Sysinternals, or:
Get-Process | Where-Object {$_.Modules.FileName -like "*yourdb.db*"} -ErrorAction SilentlyContinue
```
More reliably, use Sysinternals `handle.exe yourdb.db` if it's available on the box — PowerShell alone doesn't have a clean built-in way to check open file handles.

**6. Check who owns the file vs. who's running the service**
```powershell
(Get-Acl "C:\path\to\yourdb.db").Owner
Get-WmiObject Win32_Service -Filter "Name='YourServiceName'" | Select-Object StartName
```
Compare the service's `StartName` (the account it runs as) against what has write access from step 1.

**7. If it's on a mapped/network drive, confirm it's still writable at all**
```powershell
New-Item -Path "C:\path\to\folder\testwrite.tmp" -ItemType File -Force
Remove-Item "C:\path\to\folder\testwrite.tmp"
```
If this fails under an admin PowerShell session but the app still fails under its own service account, it's almost certainly a permissions/identity mismatch rather than a filesystem-wide issue.

Given it happened "suddenly," I'd run **#2, #3, and #4 first** — those are the ones that commonly flip overnight without anyone touching permissions (a backup job resetting an attribute, a stray journal file from a crash, or the disk just filling up).
